# Ashwin Baduni

Personal site of Ashwin Baduni, co-founder of [MihawkAI](https://mihawk.ai).

**Live:** [ashwin-baduni.github.io](https://ashwin-baduni.github.io)

## Stack

- Vite, React and TypeScript
- Tailwind CSS v4
- GSAP (ScrollTrigger, ScrollTo) for motion
- A hand-drawn canvas site plan in the hero
- Self-hosted fonts: Newsreader, Inter Tight, JetBrains Mono

## Develop

```bash
npm install
npm run dev      # local dev server
npm run build    # production build into dist/
npm run preview  # serve the production build locally
npm run verify   # every check below, in order
```

The About word reveal uses 30% more scroll distance only in the wide composition. Phone reading distance is unchanged. The phone preview target is `15svh`; the planner keeps incoming content below the current card and its clearance. Desktop has no waiting section previews. Phone diagram sizes retain their existing allowance.

Main copy and links live in `src/content.ts`; animated examples live in their demo components. The page runs through Introduction, About, MihawkAI, Kehsun, Skills, Experience, Projects and Certifications. The CV preview uses `public/files/CV.pdf`.

## Responsive layout and motion

Wheel, trackpad and touch input remain native. On wide layouts with a fine pointer, an idle gesture can finish moving to the adjacent section once a small slice of that section is visible (about 3% of viewport height), rather than waiting for half the gap. The gesture remembers its starting destination: a short movement finishes towards it and a single movement that overshoots returns to it. Renewed impulses, reversals and sustained scrolling release that destination, so repeated input can continue through the page. The optional `WheelEvent.momentum` signal is used where available; otherwise gesture grouping uses timing and delta trends, not device detection. This is a heuristic and cannot infer every physical finger lift.

The settling motion is modelled on falling through a tunnel through the earth: the section pulls the page with a force that grows with the distance from it, as gravity does inside a planet, so every fall reaches the section in 0.3s from wherever it begins and only the speed differs. Falling in loses nothing, so the page is fastest exactly at the section. Flying out, the pull acts like a rubber band that absorbs energy as it stretches: the braking builds from nothing at the section, and each overshoot keeps a third of the swing before it (the first, a third of the pull), on alternate sides, every swing out taking the same time, until the next would be under 0.3% of the screen and it glides into place. Like a falling object's top speed, no pull arrives faster than one whose overshoot reaches 15% of viewport height; a longer pull falls under a proportionally gentler pull and takes longer instead, so the band never changes. No length is a pixel value (`settleMotion` in `desktopSettle`). Once scrolling stops between two sections, after a single small movement, several quick ones or input that interrupted a settle, the page goes on to the next section in the direction it was moving, however little of it shows, so a low-sensitivity wheel is never sent back. Actual scrolling covers only the pull: from its arrival the page rests at the destination while an independent decorative translation supplies the swing and bounces, including on sticky cards and the page-end footer, without advancing a demonstration or adding page height (desktop `#main` clips its vertical overflow). Every section the swing could bring into view shares that translation, on either side, so the gaps between them keep their size, and scroll anchoring is off while it lasts, since Firefox's anchoring follows translations. If native inertia has already passed the destination, the section pulls the page back and the swing goes past it on the other side. A gesture starting inside a demonstration remains native until it exits. Fresh input cancels automatic scrolling immediately; any remaining decorative offset relaxes over 0.12s. Navigation, resizing and layout refresh clear it synchronously. Phones, coarse-pointer input and reduced motion are excluded (`useDesktopSettle`, with pure intent and gesture helpers in `desktopSettle`). A layout change never moves the page by itself, with one deliberate exception: after a width change such as rotation, or when a section switches between its narrow and wide arrangements, the page returns to the card or passage being read, at the same point of its demonstration, unless the visitor has already scrolled, touched or pressed a key. Scroll progress drives the stories in both directions. A non-interactive Scroll cue sits at the opening viewport edge and fades as scrolling begins.

- **Browser-held stories:** every waiting, parked or leaving element is positioned by the browser with `position: sticky`, which compositors apply during asynchronous scrolling. JavaScript never moves a story element per frame; it only fades cards and plays each parked card's demonstration. Each card sits in its own lane, an absolutely positioned box ending at the story's common exit. A transparent spacer at the top of the lane lets the sticky card be lifted over it: its sticky `bottom` keeps a waiting card's top at the preview line, `top` parks it, and the lane's end releases it together with the rest. `src/lib/storyPlan.ts` computes these lengths as plain numbers. `src/lib/storyLayout.ts` measures every story in one batched pass whenever fonts, text size, content or the viewport change, then refreshes ScrollTrigger once. A refresh rewinds each animation to measure and restores it silently, so each story redraws the wording its demonstrations draw (typed questions, plate characters, review notes) from the restored progress.
- **Product, skill and project cards:** `useCardStack` keeps the introduction above a sequence of fully overlapping cards. Each card arrives (the first one rising into view faintly from the bottom edge), parks and plays its demonstration. The next card already waits faintly in the bottom 15% of the small viewport, reduced only when needed for clearance from the moment the current card parks. Once the demonstration has been read, it rises with the page and is solid before it parks. Its own demonstration starts only after parking. Introduction words fill during arrival. Skills uses a small blue label above the changing capability title, with one `01 / 04` counter inside each illustration; each card keeps its own words for assistive technology.
- **Products on a wide screen:** where two cards of at least 28em fit side by side, MihawkAI’s Vision Tech and Yoru, and Kehsun’s people and practitioner demos, form rows below their introductions instead of stacks (`useCardRow`, planned by `planRow`). The story's own width decides, through a CSS container query, so a narrower parent or larger text changes it as well as the window; landscape phones keep the stack. The row rises into view as one, like a stack's first card, and parks with its introduction and cards vertically centred as one composition. Both cards stay level and as tall as the taller one; each card reads top to bottom, and Vision's camera fills its card's width at its own proportions. Then both demonstrations play together over one stretch of scroll, each with its own steps. The completed row stays fully visible for a quarter of a screen before the story leaves and fades, and the following section arrives in normal flow. There is no waiting next-section preview in the wide presentation. Vision's camera may shrink to fit a short window, keeping its proportions; if the row still cannot be held (a very short window, or reduced motion), the cards stay side by side in normal flow, finished. Between phone and desktop widths, where the stacked cards read top to bottom but are wide, the camera shrinks in the same way so the stack stays held. It shrinks only where it is wider than 28em and never below 20em, so phones are never affected (`fitPicture`). Only one controller owns the story at a time: a change of arrangement is found at the start of a layout pass (`useStoryArrangement`), the previous controller is reverted completely, and the other joins that same pass.
- **Desktop scrollbar:** the bright sky-blue to baby-pink palette gradient on both root and body scrollbar pseudo-elements, since Chromium can paint the viewport thumb using the body style, with a solid sky-blue Firefox fallback. A screenshot-pixel regression checks the painted colours, not only computed styles. Narrow layouts retain their earlier styling.
- **Desktop closing sections:** Projects keeps a viewport of reading space; Certifications is a compact, content-sized footer just after it. The last settling destination clamps to the document end, revealing Certifications without an extra full-screen section, with Back to the top near the bottom edge. The footer clips entrance transforms so the return link cannot temporarily extend the scroll limit. Phones keep their existing spacing.
- **Between sections:** on phones, `useSectionHandoffs` lets the next section's real introduction wait faintly below the final parked card. Its lane reaches back over the previous story, so the browser holds it; it then rises in normal flow and joins its section. It always keeps a clear gap from the outgoing content, faint or solid. The outgoing story fades as it leaves. Desktop introductions arrive in normal flow without preview lanes. Introduction fades finish within the page's actual scroll limit, so a short closing section stays fully readable at the bottom.
- **Skills on a wide screen:** all four chapter links stay visible on the left. All four descriptions remain expanded beneath their names, with fine separators between rows. The active name has a pink highlight; all row separators remain neutral. `useSkillSequence` owns one native sticky illustration frame on the right; diagrams assemble, hold, then fade out/in without overlapping. Each chapter has a reading interval and a link to its completed state. The complete list has an intrinsic, stable height; chapter selection never moves the text. The illustration frame aligns precisely from the first skill heading to the last description line, excluding the Skills label. The SVG scales proportionally within that measured height; headings and captions keep their text sizes. The composition is centred in the full available height; shorter screens reduce that offset without shrinking the content. Experience arrives naturally after the sequence. Separators appear only between skills, never below the Skills label. `skillPlan` defines the pure chapter geometry; opacity and assembly reverse with scrolling. The same 57.5em container boundary selects this presentation. Short windows and reduced motion show all four complete cards in normal flow; narrower layouts keep the phone sequence.
- **Projects:** on wide screens, an intrinsic CSS grid shows Video motion amplification spanning the left column, with Analytics chatbot above CAPTCHA recognition on the right. The complete grid scrolls naturally, with reversible arrival fades and the existing visible-only loops. It has no stack waiting spacers and no fixed height that can clip larger text. Below the same readable-width boundary, Projects keeps the same card stack as Skills. The Projects heading settles first while Video motion amplification continues rising for a short, viewport-relative distance before parking below it. Analytics chatbot previews as soon as there is clear space beneath the arriving card, then rises and covers it; CAPTCHA recognition follows the same sequence, with Certifications waiting below. Early preview time counts towards the wait, so parking does not restart it; each card still keeps its full reading interval before the next card reaches it. Project cards have looping visuals instead of scroll-played demonstrations, so each is held for a shorter reading time, and each loop plays only while its card is on show.
- **Sizing:** shared CSS `--story-*` tokens use bounded viewport- and font-relative spacing, resolved by a hidden probe. Scroll distances use the small viewport (`svh`), which stays stable while browser toolbars retract; a waiting preview follows the visible bottom edge. Actual content dimensions decide card heights and whether a composition fits. No phone model selects the layout.
- **Adaptation:** a stacked product first tries the complete composition with its introduction held above its cards. Where that cannot fit, both MihawkAI and Kehsun let the introduction scroll away and use the available height for the same animated card stack (`data-intro="flow"`). Where even the cards and their previews cannot fit, the cards stay in readable normal flow and their demonstrations still scrub forwards and backwards as each card passes through the viewport (`data-playback="flow"`); lack of space does not silently disable playback. Reduced motion always shows the finished, static layout. Skills and the wide product rows retain their existing fit fallbacks; wide Projects uses normal flow (`data-story-fit` explains an unheld layout). Chapter links also work in plain layouts. Keyboard focus that lands in a waiting or covered card, or a faint introduction, brings it to where it is solid and uncovered. After a width change such as rotation, or a change of a section’s arrangement, the page returns to the card or passage being read, unless the visitor has already moved on; other toolbar and text-size changes never move the page.

## Checks

```bash
npm run typecheck     # TypeScript, including the tests
npm run lint          # oxlint: TypeScript, React and React Hooks rules
npm run check:static  # unreachable files, unused CSS, no positioning in the story hooks
npm run test:unit     # storyPlan against an independent model of the sticky rules
npm run test:e2e      # build, then the browser checks in tests/e2e
npm run compare:checkpoint -- --sizes 412x812,430x932,768x1024  # strict comparison; reports intentional content changes too
```

The browser checks use Playwright with its own isolated browsers (`npx playwright install chromium firefox webkit` once). They run Chromium, Firefox and WebKit at phone size and at desktop size (MihawkAI's row at six desktop sizes, its fallbacks, its arrangement boundary and repeated switching in all three engines; the shared story, frame and gesture checks in Chromium), plus a React StrictMode run against the dev server. Every check judges rendered DOM rectangles, composited frames or page behaviour, never the planner's own numbers. They cover held elements never moving per frame, clearance between stories, the wait, rise, park and exit sequence, finished demonstrations, interrupted gestures and fast passes, a viewport matrix (14 sizes in Chromium; short portrait, mixed, tall portrait and landscape in Firefox and WebKit), live resizing and fit-boundary crossings, toolbar-sized height changes, rotation, 125 to 200% text, reduced motion, shared and in-page links, keyboard focus, email copying, the CV preview and back-to-top. Any page error or console warning fails a check, as does a programmatic scroll caused by a toolbar-sized or text-size change; after rotation, the card being read must be on show again. A replay check confirms that the project loops never retain earlier runs' animations, and a switching check that MihawkAI's controllers never accumulate. Switching between the row and the stack in the middle of both demonstrations must continue from the same point and, scrolling forward and back, show exactly what a fresh page shows (plate characters, scan, zoom, record, question, status, results and history). Completed demonstrations must keep their finished wording through a re-layout. `npm run compare:checkpoint [ref]` builds another commit in a temporary folder beside the working tree and compares the two at phone and narrow sizes, scrolling down and back up with the page clock under its control: every rectangle, fade, inline style, story attribute, changing text and loop state must match, to the half pixel, and any smaller deviation is reported. A difference counts only if it persists after both pages are given more time at that position. `--self` compares the checkpoint with itself, which shows the variability the page already had: Firefox at 768×1024 settles its handoff headings anywhere within a 1px band and its hero recede at slightly different offsets from one load to the next. `BASE_URL=http://host:port npx playwright test` runs the same checks against another server. On a host without WebKit's system libraries, set `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1` to opt in to skipping Playwright's host check.

Real phones still need a final look: iOS Safari's toolbar collapse with sticky previews, real touch momentum, and system text-size settings cannot be reproduced in headless browsers.

The short-window product regression tests require MihawkAI and Kehsun to animate, finish and reverse at 445×570, 494×633, 500×657, 600×657 and 375×548. They also cover normal-flow playback in landscape, reduced motion and live resizing between arrangements. A static fallback is not accepted as a passing animation check. The checkpoint comparator without `--sizes` still includes the older short and landscape layouts; those now intentionally differ because their static product demos have gained playback. The IRM certification now puts Level 1 on a separate line without a comma, as requested; the strict historical comparator reports this intentional content/height difference too. The wide-layout audit compares phone story geometry, styling, progress and loop state against the immediately preceding build through the start of Certifications, excluding only that requested footer change. Behavioural regression tests cover the improved short layouts.

Implementation references: [sticky positioning](https://drafts.csswg.org/css-position-3/#stickypos-insets), [scroll-linked effects and asynchronous scrolling](https://firefox-source-docs.mozilla.org/performance/scroll-linked_effects.html), [small and dynamic viewport units](https://web.dev/blog/viewport-units), [container size queries](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_size_and_style_queries), [bounded fluid sizing](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/clamp), and [ScrollTrigger refresh](https://gsap.com/docs/v3/Plugins/ScrollTrigger/).
